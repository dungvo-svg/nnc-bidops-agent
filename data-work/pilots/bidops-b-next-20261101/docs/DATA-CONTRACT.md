# Data contract — bidops-pilot/1

1. `Source` is identified by source_id+version and a content SHA256, with observed_at and locator. Repeating identical intake is a no-op; reusing source_id/version with another digest is a conflict. Source payload is not copied into the ledger. Source version changes never silently replace approved evidence.
2. `Quote` is one supplier offer for one explicit product variant, unit, currency, basis, validity dates and source version. Item code/MPSC is a lookup hint; the exact variant ID is mandatory. Quote id is immutable. Missing validity/unit/basis is unresolved, never zero/current by assumption.
3. `Requirement` is package_id+requirement_id+version, exact variant, unit and source version, plus optional destination mapping. A common offer may serve more than one requirement after independent qualification; it is stored once.
4. Qualification returns technical/unit/date/source/ destination blockers and three evidence axes: goods, documents, money. Axis true means the synthetic evidence object exists with reference, not legal acceptance. No quote is auto-approved. Candidate content is hashed with requirement+quote versioned data and current source pointers.
5. `Node` contains owner_id+agent_id and explicit pilot capabilities. A `Mission` has immutable mission_id, owner node, requirement pointer, scope, source-version manifest, deadline and expected output. Issued is not received; received is not returned; returned is not approved. Actor must match the owning node for receive/return. Source drift blocks return/promotion, preserving the old event history.
6. Every event has unique event_id and canonical payload digest. Exact retry returns the same receipt; same ID with changed actor/payload/type is rejected. Retry does not generate new task or approval. Receipt proves local persisted state only.
7. Review records the reviewer actor label (fixture node/owner/agent strings, not an authenticated principal), candidate digest, evidence reference and explicit decision. Application requires an unmodified reviewed candidate and a principal with `candidate_apply`; use requires explicit `candidate_use`. These capabilities exist only in synthetic config. No event mutates an Excel master, sends an offer or submits a tender.
8. New quote or source version cannot inherit review/apply/use from a prior candidate. Missing destination is an exception, not dropped data. Expired/current-not-proven means blocked/unknown, never valid by sheet title. All dates are ISO dates; timestamps UTC.
9. Business authorization is separate from pilot capabilities. Real equivalents, supplier/price commitments, portfolio, canonical writer and submission identity are never inferred from job title, CEO status or account access.
10. Operational measurement counts unique reviewed/applied/used candidate receipts by a defined period and grain. Raw quote-option rows, demand rows, messages and attachment backfills cannot be divided as an acceptance conversion rate.

## Demand lifecycle amendment — Dũng 31/10/2026

11. The common catalog includes Komsenahak along with the other active packages. One `tender_case` owns versioned `case_line` rows and `demand_link` records to `normalized_variant`; source quote versions are shared, never copied into per-hospital masters. Normalized identity must retain MPSC, specification, UOM and registration/validity distinctions when present; incomplete identity remains unresolved rather than merging by code/name alone.
12. The active sourcing worklist is derived from active demand links. Closing/cancelling an explicitly confirmed case removes only its prebid demand; a variant needed by another case remains. Do not delete variants, source quotations, history or provenance. Reopening a case restores eligible demand through a new event, not an overwritten historical state.
13. A scheduled deadline does not prove the package ended: represent planned closure, extension, cancellation and overdue-unknown. Mere clock passage cannot automatically mark a package closed, won or lost. Deadline extension is a versioned event. Late quote/mission events cannot silently reactivate a closed case.
14. Separate `prebid_sourcing` from `fulfillment` demand. Fulfillment demand is accepted only for an explicitly `won` case, in both `Ledger.link_demand` and `catalog_lifecycle.create_fulfillment` (enforced 02/11/2026). A won package may stop prebid sourcing while retaining purchasing/delivery needs until explicitly fulfilled/cancelled. Derive views per need type, show unknown lifecycle status rather than hiding it, and preserve receipts when a case is reopened or extended.
15. SQLite is the pilot state owner. Human-facing CSV/Excel exports are projections when requested, not a second master and never input authority by accidental edit. This amendment authorizes synthetic/local lifecycle implementation and read-only extraction of the actual 1,455 Kom rows; it does not authorize deleting/updating real master data or changing live case status.

## Useful exception consumption

16. A mismatch or missing destination is useful returned work. A consumer may explicitly record `used_in_candidate` for a HOLD/diagnostic output with its evidence reference, even though the offer remains unapproved and unapplied. Keep diagnostic-consumption receipt separate from commercial reviewed/applied/used state and throughput. A 40mm quote checked against 30mm demand must be returnable and consumable as a HOLD decision, never promoted as a compatible offer. Source drift invalidates downstream consumption of old analysis; exact retry remains idempotent.

## B-next lifecycle amendment — technical pilot, 02/11/2026

These are synthetic pilot invariants, not business decisions or LOCKED requirements.

20. Each explicit reopen starts a new case scope (`case_epoch` = count of reopen events). Candidates and missions pin the epoch they were created under; after a reopen they are history only. Review, apply, use and late mission return are blocked until a new mission/candidate is produced in the new scope.
21. Extension (`extend_case_deadline`) must be strictly later than the current deadline. `set_case_deadline` is a correction; an earlier correction is recorded with `backward_correction_policy = pending_business_decision`. Whether backward corrections need extra approval is not decided by the pilot.
22. `WorkpackInbox.export_packet` writes a new local JSON file (exclusive create) only for a current REVIEWED draft whose source scope still matches the catalog. Owner/agent stay null, `dispatch_allowed` false, delivery `LOCAL_FILE_EXPORT_NOT_SENT`. Nothing is sent.
23. `import_return` records a returned file as `RETURN_UNVERIFIED` (or `RETURN_HISTORY_ONLY` when the draft is stale/cancelled/inactive). Claimed owner/agent are unverified claims; no draft, slot, owner or business state changes. Exact retry keeps the receipt; changed content under the same event_id conflicts.
24. Case authority is single. `catalog_bridge.read_case_snapshot` reads the catalog read-only; `Ledger.adopt_case_snapshot` projects it with a hash check, a compare-and-set on the previous snapshot hash, and a rule that lifecycle history only grows (no rollback). Once bound, Ledger-side close/reopen/deadline writes for that case are refused. Ledger and catalog never share one SQLite file.
25. A planning date is not a legal closing instant: `official_closing_at` stays null unless the catalog has it. Passing either one shows `overdue_unknown`; nothing closes by clock. Candidates pin the case snapshot hash; a changed snapshot requires requalification.
26. `catalog_bridge.bridge_variant` returns HOLD for an unresolved line. A BRIDGED variant comes only from an explicit reviewed `line_resolution`, never from MPSC/name/UOM similarity. `Ledger.intake_bridged_variant` stores it with per-line provenance (catalog identity hash, evidence ref, reviewer label, source anchor).
27. Qualification may take fixture certificate/portfolio checks with their own source refs (pinned in the manifest). Identity conflict/unknown, expired axes and portfolio issues become blockers. The five business assessments (dossier compliance, supply capability, economics/working capital, competitive basis, actual outcome) are reported separately as `unknown` with a reason or `checked_fixture_only`; there are no scores and no approval.
